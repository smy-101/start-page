对 `main` @ `5515f13` 的构建产物,在 5000 条收藏量级下实测首屏与交互指标。
**用途:为工单 10 的性能预算与技术方案选型提供一手数据(进 `/grill-with-docs` 敲定)。**

| 项       | 值                                                                                                                                                       |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 扩展构建 | `npm run build` @ `5515f13`,CDP `Extensions.loadUnpacked` 到 `C:\dev\start-page-dist`                                                                    |
| 浏览器   | Windows Chrome 156,调试 profile `C:\chrome-mcp\start-page-e2e`(现留有 5000 条性能测试数据,可复用)                                                        |

| 计量方式 | 冷加载:`about:blank → 扩展页` 确定性导航,MutationObserver 判定卡片数到位;交互:同步段 `performance.now()` 包裹 dispatch(3 轮取稳定值)+ 时间线采样交叉验证 |

**方法学教训(读数时注意)**:轮询型计时在主线程被同步渲染阻塞时会饿死,时间戳标签失真;「谓词首次为真」时刻 ≠ DOM 提交时刻。本报告交互数字以同步段计量为准。

## 存储写放大

`chrome.storage.local.set` 全量 state(568KB)单次实测 **60–287ms**(3 次:71/287/60)。
当前**每次增删改都全量重写**,且 `App.tsx` 的 `adapter.subscribe → boot()`(重建整个 store)与 `refresh()`(再次 setState)叠加,单次变更 = 1 次全量写 + 2 次全树重渲染。

## 代码级瓶颈定位(供方案讨论)

1. **全量持久化**:`chromeStorage.ts` 单键 `state` 整体读写,量级成本随收藏数线性上涨。
2. **变更双重渲染**:`App.tsx` 订阅 `storage.onChanged` 重建 store + `run()` 成功路径再 `refresh()`,一次变更两次全树提交。
3. **零 memo 化**:`BookmarkGroups.tsx` 每渲染重建 `filter + sort` 数组,`GroupSection`/`BookmarkCard` 无 `React.memo`,任一状态变化(含输入搜索词的每个字符)全卡重渲染。
4. **无虚拟化**:5000 条 = 41.7k DOM 节点全量挂载,重挂成本即首屏成本。

## 待决策(进 `/grill-with-docs`)

- 性能预算数字:5000 条下首屏/交互各定多少?(实测基线:首屏 0.6s、最差交互 ~1s)
- 方案取舍:虚拟滚动 / 分组懒渲染(折叠默认+渐进展开)/ memo 化 + 渐进渲染 / 存储分片增量写——实测显示「重挂/重渲染」是主要矛盾,「全量写」是次要矛盾(60–290ms)。
