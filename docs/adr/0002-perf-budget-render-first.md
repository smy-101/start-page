# 性能预算与渲染优先策略(不做虚拟化)

spec story 36 要求「数千条收藏后初始页依然流畅」。2026-10-29 实测(`docs/perf-5000-2026-10-29.md`):5000 条首屏 592ms、最差交互 ~1s,瓶颈是**重挂载与全树重渲染**(卸载仅 ~1ms),全量 storage 写(60–287ms)是次要矛盾。决定:**5000 条为设计点,超出按线性降级不专门优化**;预算 = 首屏 ≤500ms、纯 UI 交互 ≤100ms、存储链路交互(增删改)≤300ms;路线 = 渲染修复(memo 化、消除每次变更的双重提交、派生数组缓存)+ 懒挂载(新分组默认折叠),**不引入虚拟化、不做存储分片**。升级触发:两措施落地后仍有任一指标超预算 1.5 倍,才重新决策(需新 ADR)。

## Considered Options

- ~~虚拟滚动~~:保证最强,但网格布局与拖拽交互需重做,实测预算用不到。
- ~~存储分片/增量写~~:写成本异步且非感知瓶颈,仅在存储链路 300ms 预算失守时再启。
- ~~初始限量挂载(每组前 N 张 + 展开全部)~~:实现最复杂,留作懒挂载不达标后的后手。

## Consequences

- 性能防回归走**行为断言**(vitest:折叠组零挂载、单变更单提交、相同 props 不重渲染),时间阈值不进 CI;手动复测用 `scripts/perf-probe.mjs`(工单 10a 整备入库)。
- 「新分组默认折叠」是产品行为变更:老用户持久化的折叠状态不动,仅新分组/全新安装初始折叠。
